## 목적
GitHub 레포 주소(1개 이상)를 받아서 "저게 우리 프로젝트에 어울리는가"를 실제로 코드까지 열어보고 판단한다. README만 읽고 감으로 답하지 않는다 — 인기 있는 레포라고 오버셀하지 말고, 안 맞으면 안 맞다고 정직하게 말한다.

## 핵심 원칙
레포 소개가 아니라 **fit 판정**이 결과물이다. "이 레포는 이런 걸 한다"에서 끝내지 말고, 반드시 "그래서 우리가 지금 가진 것(기존 코드, 스택, 데이터 소스, 운영 여력)과 비교했을 때 통째로 도입/부분 차용/비적합 중 뭐가 맞는지"까지 결론 내린다.

## 절차

1. **현재 프로젝트 컨텍스트 파악**
   - 작업 디렉토리의 `CLAUDE.md`, `docs/` 등을 읽어 우리 스택·아키텍처·제약을 정리한다 (프로젝트마다 다르므로 하드코딩하지 말 것 — CLAUDE.md가 없으면 `package.json`/`requirements.txt`/`pyproject.toml` 등으로 스택을 역추론).
   - 이 프로젝트(finance-dashboard)라면: Flask+pandas 백엔드, React 19+TS+Zustand+TanStack Query+Chart.js 프론트, 로컬 엑셀 파일이 데이터소스(라이브 DB 없음), CLAUDE.md의 레이어 의존성 규칙(`types→utils→api→store→hooks→ui→features→pages`) — 같은 제약을 반드시 비교 기준에 넣는다.
   - 사용자가 평가 목적을 명시했으면(예: "위젯 아이디어용" vs "전면 교체용") 그 기준으로 좁혀서 본다. 안 밝혔으면 기본은 "전면 도입 가능성 + 부분 차용 가능성" 둘 다 본다.

2. **스크래치 디렉토리에 clone**
   - 프로젝트 디렉토리 밖, 예: `/tmp/repo-fit-check/<repo-name>` 에 `git clone --depth 1 <url>`.
   - 절대 작업 중인 프로젝트 레포 안에 clone하지 않는다 (git 상태 오염 방지).
   - 레포가 여러 개면 전부 이 단계에서 clone해둔다.

3. **레포별 조사 (Explore 서브에이전트, 병렬 파견)**
   레포 개수만큼 `Agent` 툴로 `subagent_type: Explore`를 동시에 띄운다(독립 조사라 병렬이 맞다). 각 에이전트에게 아래를 조사시킨다:
   - **목적**: README 기준 이 레포가 스스로 뭐라고 주장하는가
   - **아키텍처/스택**: package.json, requirements.txt, Dockerfile, docker-compose.yml 등으로 백엔드/프론트 스택 확정
   - **데이터 모델**: 어떤 데이터를 다루도록 설계됐는가 (mock 데이터인가, 실제 DB 연동을 전제하는가, 로컬 파일을 지원하는가)
   - **기능 구현 방식**: 대시보드/페이지가 코드로 직접 짜야 하는 구조인지, 설정만으로 되는 no-code/low-code 구조인지
   - **배포 복잡도**: 컨테이너/서비스 몇 개가 필요한지 (DB, 캐시, 워커 등 추가 의존성 여부)
   - **커스터마이징 유연성**: 디자인/테마를 우리 것으로 바꾸는 게 쉬운지, 특정 UI 킷에 강하게 종속되는지
   - **유지보수 상태**: 최근 커밋/릴리즈로 활발히 관리되는 프로젝트인지

4. **종합 판정**
   레포마다 다음 세 가지 중 하나로 명확히 결론짓는다:
   - **전면 도입 가능** — 스택/데이터소스/운영부담이 실제로 맞아떨어지는 드문 경우
   - **부분 차용 권장** — 플랫폼 전체는 안 맞지만 특정 위젯/패턴/컴포넌트는 지금 스택에 그대로 이식 가능 (구체적으로 어떤 파일/컴포넌트를 참고하면 되는지 지목)
   - **비적합** — 왜 안 맞는지 구조적 이유를 짚는다 (스택 불일치, 데이터소스 가정 불일치, 마이그레이션 비용이 이득보다 큼 등)
   레포가 여러 개면 표로 비교하고 최종 추천을 한 문단으로 정리한다.

5. **정리**
   - 분석에 쓴 clone은 임시본이라고 안내한다 (`/tmp/repo-fit-check/`) — 필요 없으면 지워도 되고, 남겨서 다음에 또 물어봐도 된다는 정도로만 언급. 먼저 나서서 삭제하지 않는다 (사용자가 더 볼 수도 있음).

## 주의사항
- clone은 항상 `--depth 1` (전체 히스토리 불필요, 속도/용량 낭비 방지)
- 레포가 크더라도 Explore 에이전트에게 "token 예산 신경쓰지 말고 철저히 보라"고 지시해도 된다 — 이 스킬의 가치는 얕은 요약이 아니라 실제로 코드 열어본 근거에 있다
- README의 마케팅 문구를 그대로 믿지 말 것 — package.json/requirements.txt 등 1차 자료로 직접 확인한 사실만 결론에 반영
- 사용자가 이미 비슷한 검토를 과거 세션에서 했을 수 있다 (`docs/session-log.md` 확인) — 중복 조사면 그 기록부터 참고하고 새로 볼 부분만 추가 조사
